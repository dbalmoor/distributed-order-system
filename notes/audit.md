# As-is audit for the distributed order-management system

## 1. Service and module layout

The repo is split into six Maven modules, each with its own `pom.xml` and no repo-root parent aggregator visible in the repo contents:

- [common-dto](../common-dto)
- [gateway-service](../gateway-service)
- [inventory-service](../inventory-service)
- [order-service](../order-service)
- [payment-service](../payment-service)
- [saga-orchestrator](../saga-orchestrator)

This matches the intended architecture in requirement.md: order, inventory, payment, saga orchestrator, and a shared DTO module. The only compose file present is [docker-compose-kafka.yml](../docker-compose-kafka.yml), which starts ZooKeeper, Kafka, and Kafka UI only; there is no full multi-service deployment file for all services and databases.

## 2. Actual behavior by service

### Order service

- REST API is defined in [OrderController.java](../order-service/src/main/java/com/deepana/orderservice/controller/OrderController.java): `POST /orders`, `GET /orders/{id}`, `GET /orders/number/{orderNumber}`, `GET /orders/user/{userId}`, and `PUT /orders/{id}/cancel`.
- Create flow: `OrderServiceImpl.createOrder(...)` persists a new `Order`, sets `status = CREATED`, builds a random `sagaId`, builds an `OrderCreatedEvent`, and sends it immediately through `orderEventProducer.sendOrderCreated(event)`; it does not persist an outbox row in the same transaction. See [OrderServiceImpl.java](../order-service/src/main/java/com/deepana/orderservice/service/OrderServiceImpl.java) and [OrderEventProducer.java](../order-service/src/main/java/com/deepana/orderservice/kafka/OrderEventProducer.java).
- Order status transitions are handled in `OrderServiceImpl` methods: `handleInventoryReserved`, `handleInventoryFailed`, `handlePaymentSuccess`, `handlePaymentFailure`, `confirmOrder`, and `cancelBySaga`. The checks are local `if` guards, not a centralized state machine. See [OrderStatus.java](../order-service/src/main/java/com/deepana/orderservice/entity/OrderStatus.java).
- The order entity is [Order.java](../order-service/src/main/java/com/deepana/orderservice/entity/Order.java). It has fields `orderNumber`, `userId`, `totalAmount`, `status`, `items`, timestamps, and a `paymentPending` flag. It does not appear to store a saga state or a saga id besides the event metadata that is sent to Kafka.

### Inventory service

- Command consumers listen to `inventory.reserve.cmd` and `inventory.release.cmd` in [InventoryCommandConsumer.java](../inventory-service/src/main/java/com/deepana/inventoryservice/kafka/InventoryCommandConsumer.java).
- `InventoryServiceImpl.processReserve(...)` performs an idempotency check via `processedRepo.existsBySagaIdAndEventType(...)`, then resolves inventory rows with `findByProductIdForUpdate(...)` from [InventoryRepository.java](../inventory-service/src/main/java/com/deepana/inventoryservice/repository/InventoryRepository.java), updates available/reserved quantities, persists `Inventory`, and then writes a `ProcessedInventoryEvent`. See [InventoryServiceImpl.java](../inventory-service/src/main/java/com/deepana/inventoryservice/service/InventoryServiceImpl.java).
- `InventoryServiceImpl.processRelease(...)` does the same pattern in reverse (restore stock and mark processed). See [InventoryServiceImpl.java](../inventory-service/src/main/java/com/deepana/inventoryservice/service/InventoryServiceImpl.java).
- The inventory service emits `inventory.reserved` and `inventory.failed` on success/failure through [InventoryEventProducer.java](../inventory-service/src/main/java/com/deepana/inventoryservice/kafka/InventoryEventProducer.java).

### Payment service

- The payment command consumer is [InventoryEventConsumer.java](../payment-service/src/main/java/com/deepana/paymentservice/kafka/InventoryEventConsumer.java) and it listens to `payment.charge.cmd`.
- `PaymentServiceImpl.processPayment(...)` writes a `Payment` row and then emits either `payment.success` or `payment.failed` via [PaymentEventProducer.java](../payment-service/src/main/java/com/deepana/paymentservice/kafka/PaymentEventProducer.java). The success/failure is generated by a `Random` value (`random.nextInt(10) < 8`) and a forced failure when `totalAmount == 10000`. See [PaymentServiceImpl.java](../payment-service/src/main/java/com/deepana/paymentservice/service/PaymentServiceImpl.java).
- There is no payment-level idempotency guard or processed-message table in the payment service. The repository is a plain `JpaRepository` with no unique constraint or natural-key dedupe check. See [PaymentRepository.java](../payment-service/src/main/java/com/deepana/paymentservice/repository/PaymentRepository.java).

### Saga orchestrator

- The orchestrator listens to `order.created`, `inventory.reserved`, `inventory.failed`, `payment.success`, and `payment.failed` in [SagaEventConsumer.java](../saga-orchestrator/src/main/java/com/deepana/sagaorchestrator/kafka/SagaEventConsumer.java).
- Each listener calls a stateless service method in [SagaServiceImpl.java](../saga-orchestrator/src/main/java/com/deepana/sagaorchestrator/service/SagaServiceImpl.java), which sends commands such as `inventory.reserve.cmd`, `payment.charge.cmd`, `order.cancel.cmd`, `inventory.release.cmd`, `order.confirm.cmd`, and `payment.refund.cmd` by calling `SagaCommandProducer`.
- There is no dedicated saga-persistence layer in the orchestrator for crash recovery. `OrderSaga.java` exists but is not a live component of the logic. The entity stores only `sagaId`, `orderId`, `status`, `step`, and timestamps; there are no repositories, transition logs, or resumption handlers. See [OrderSaga.java](../saga-orchestrator/src/main/java/com/deepana/sagaorchestrator/entity/OrderSaga.java).

### Gateway service and common DTO module

- [gateway-service/src/main/resources/application.yaml](../gateway-service/src/main/resources/application.yaml) forwards `/orders/**`, `/payments/**`, and `/inventory/**` to the service ports.
- [common-dto/src/main/java/com/deepana/saga/commondto/base/BaseEvent.java](../common-dto/src/main/java/com/deepana/saga/commondto/base/BaseEvent.java) defines the common metadata (`sagaId`, `orderId`, `traceId`, `timestamp`, `orderNumber`).
- Shared DTO classes such as `OrderCreatedEvent`, `ReserveInventoryCommand`, `ChargePaymentCommand`, and others are in [common-dto/src/main/java/com/deepana/saga/commondto](../common-dto/src/main/java/com/deepana/saga/commondto).

## 4. Outbox status in the codebase

### What exists

- `OutboxEvent` is defined in [OutboxEvent.java](../order-service/src/main/java/com/deepana/orderservice/outbox/OutboxEvent.java). It stores `aggregateType`, `aggregateId`, `eventType`, `payload`, `sagaId`, `traceId`, `status`, and timestamps.
- `OutboxRepository` exists in [OutboxRepository.java](../order-service/src/main/java/com/deepana/orderservice/outbox/OutboxRepository.java) with a query for `findTop50ByStatus(String status)`.

### What it does not do

- [OutboxPublisher.java](../order-service/src/main/java/com/deepana/orderservice/outbox/OutboxPublisher.java) is currently an empty class.
- No outbox row is created in `OrderServiceImpl.createOrder(...)`. Instead, it calls `orderEventProducer.sendOrderCreated(event)` immediately.
- No other service (`inventory-service`, `payment-service`, `saga-orchestrator`) has a corresponding outbox implementation or polling publisher.
- Therefore, the outbox pattern is only a partial scaffold and is not active in production. The repo is not resilient to the `DB commit -> Kafka send` gap described in requirement.md.

## 5. OrderSaga entity and crash recovery

The entity in [OrderSaga.java](../saga-orchestrator/src/main/java/com/deepana/sagaorchestrator/entity/OrderSaga.java) persists:

- `sagaId` as `@Id` (a `Long`)
- `orderId`
- `status` (`SagaStatus`)
- `step` (`SagaStep`)
- `createdAt`
- `updatedAt`

Important problems:

- `sagaId` is a `Long` in the JPA entity, but the actual event metadata uses `String sagaId` in `BaseEvent`, and `OrderMapper.toSagaEvent(...)` sets `event.setSagaId(sagaId)` with a random UUID string. This is inconsistent typing and a sign that the persistence model was never wired into real processing logic.
- There is no `OrderSagaRepository`, no `SagaStepLog` entity, and no call site that updates or fetches this entity from the orchestrator.
- `SagaServiceImpl` is stateless; it only creates command objects and sends them. There is no persisted `current_step` or `deadline`, and no code path that could resume after a crash.

Conclusion: the orchestrator cannot recover mid-saga from a crash from the code as it exists. It has a model object but not a working persistence/resume mechanism.

## 6. Idempotency by service

### Inventory service

- Inventory idempotency is implemented via `processedRepo.existsBySagaIdAndEventType(...)` in `InventoryServiceImpl.processReserve(...)` and `processRelease(...)` before mutating stock. See [InventoryServiceImpl.java](../inventory-service/src/main/java/com/deepana/inventoryservice/service/InventoryServiceImpl.java).
- The guard and the business write are in the same `@Transactional` method, which is good, but the implementation has important problems:
  - `ProcessedInventoryEvent` is not annotated with `@Entity` and `@Table`, so it may not map to a database table despite being used as a JPA repository entity. See [ProcessedInventoryEvent.java](../inventory-service/src/main/java/com/deepana/inventoryservice/entity/ProcessedInventoryEvent.java).
  - Duplicate event messages can still slip through because the repository is not guarding the publish itself; the same success message is emitted twice in `processReserve(...)` (`producer.sendInventoryReserved(successEvent);` called twice). See [InventoryServiceImpl.java](../inventory-service/src/main/java/com/deepana/inventoryservice/service/InventoryServiceImpl.java).

### Payment service

- No idempotency table, message dedupe, or unique natural key is present. Duplicate `payment.charge.cmd` deliveries can charge multiple times because there is no deterministic key check combined with the business write. See [PaymentServiceImpl.processPayment](../payment-service/src/main/java/com/deepana/paymentservice/service/PaymentServiceImpl.java) and [PaymentRepository.java](../payment-service/src/main/java/com/deepana/paymentservice/repository/PaymentRepository.java).

### Order service

- No idempotency guard for order creation or Kafka event handling was found. `OrderServiceImpl.createOrder(...)` creates one order per request and sends Kafka even if the same user repeats a request. See [OrderController.java](../order-service/src/main/java/com/deepana/orderservice/controller/OrderController.java) and [OrderServiceImpl.java](../order-service/src/main/java/com/deepana/orderservice/service/OrderServiceImpl.java).

## 7. Kafka message keys, producer config, and offset-commit behavior

### Message keys

The repo is inconsistent about keys:

- `OrderEventProducer.sendOrderCreated(...)` sends to `order.created` with key `String.valueOf(event.getOrderId())`. See [OrderEventProducer.java](../order-service/src/main/java/com/deepana/orderservice/kafka/OrderEventProducer.java).
- `SagaCommandProducer.sendReserveInventory(...)` and most command methods use `cmd.getOrderNumber()` as the Kafka key instead of `orderId` or `sagaId`. See [SagaCommandProducer.java](../saga-orchestrator/src/main/java/com/deepana/sagaorchestrator/kafka/SagaCommandProducer.java).
- `InventoryEventProducer` uses order ID as key for `inventory.reserved` and `inventory.failed`. See [InventoryEventProducer.java](../inventory-service/src/main/java/com/deepana/inventoryservice/kafka/InventoryEventProducer.java).
- `PaymentEventProducer.sendSuccess(...)` and `sendFailed(...)` do not pass a key at all (`kafkaTemplate.send("payment.success", json)` and `kafkaTemplate.send("payment.failed", json)`). That breaks per-order ordering guarantees for payment events. See [PaymentEventProducer.java](../payment-service/src/main/java/com/deepana/paymentservice/kafka/PaymentEventProducer.java).

### Producer configuration

In the producer factories, only bootstrap servers and serializers are configured. There are no explicit:

- `acks=all`
- `enable.idempotence=true`
- `retries`
- `max.in.flight.requests.per.connection`
- `linger.ms`
- `delivery.timeout.ms`

Examples:

- [KafkaConfig.java](../order-service/src/main/java/com/deepana/orderservice/config/KafkaConfig.java)
- [KafkaProducerConfig.java](../inventory-service/src/main/java/com/deepana/inventoryservice/config/KafkaProducerConfig.java)
- [payment-service/src/main/java/com/deepana/paymentservice/config/KafkaConfig.java](../payment-service/src/main/java/com/deepana/paymentservice/config/KafkaConfig.java)

### Consumer offset-commit behavior

All listeners use `@KafkaListener` with plain method parameters and default Spring Kafka consumer settings. The repo does not implement manual offset acknowledgment after database success; there are no `Acknowledgment acknowledgment` parameters and no `acknowledge()` calls. See:

- [OrderCommandConsumer.java](../order-service/src/main/java/com/deepana/orderservice/kafka/OrderCommandConsumer.java)
- [InventoryCommandConsumer.java](../inventory-service/src/main/java/com/deepana/inventoryservice/kafka/InventoryCommandConsumer.java)
- [SagaEventConsumer.java](../saga-orchestrator/src/main/java/com/deepana/sagaorchestrator/kafka/SagaEventConsumer.java)

The YAML config for the saga-orchestrator does set `listener.ack-mode: manual`, but no consumer uses `Acknowledgment`, so this setting is effectively not enforced by code. See [saga-orchestrator/src/main/resources/application.yaml](../saga-orchestrator/src/main/resources/application.yaml).

### Retry + DLQ behavior

`DefaultErrorHandler` with `DeadLetterPublishingRecoverer` does exist in several services:

- [KafkaErrorConfig.java](../inventory-service/src/main/java/com/deepana/inventoryservice/config/KafkaErrorConfig.java)
- [KafkaErrorConfig.java](../payment-service/src/main/java/com/deepana/paymentservice/config/KafkaErrorConfig.java)
- [KafkaErrorConfig.java](../order-service/src/main/java/com/deepana/orderservice/config/KafkaErrorConfig.java)
- [KafkaErrorConfig.java](../saga-orchestrator/src/main/java/com/deepana/sagaorchestrator/config/KafkaErrorConfig.java)

However, the backoff is fixed at `FixedBackOff(3000L, 2)` and there is no distinction between transient vs permanent failures, no DLQ replay endpoint or CLI script, and no metrics/alerts. This is a basic DLQ skeleton, not a full operational strategy.

## 8. Where order status transitions happen and whether illegal transitions are blocked

The explicit order states are in [OrderStatus.java](../order-service/src/main/java/com/deepana/orderservice/entity/OrderStatus.java):

- `CREATED`
- `INVENTORY_RESERVED`
- `PAYMENT_SUCCESS_PENDING`
- `PAYMENT_FAILED_PENDING`
- `FAILED`
- `CANCELLED`
- `COMPLETED`

Actual transition logic is scattered across `OrderServiceImpl`:

- `createOrder(...)` sets `CREATED`.
- `handleInventoryReserved(...)` sets `INVENTORY_RESERVED` only if the order is currently `CREATED`.
- `handleInventoryFailed(...)` sets `FAILED` if not already `FAILED`.
- `handlePaymentSuccess(...)` sets `COMPLETED` only if the order is currently `INVENTORY_RESERVED`.
- `handlePaymentFailure(...)` sets `FAILED` if the order is not already `FAILED`.
- `confirmOrder(...)` sets `COMPLETED` if the status is not already `COMPLETED`.
- `cancelBySaga(...)` sets `CANCELLED` if the order is neither `CANCELLED` nor `FAILED`.
- `cancelOrder(...)` disallows cancelling a final/terminal order in `COMPLETED`, `FAILED`, or `CANCELLED`.

This means the system does block some illegal transitions, but the transitions are not centralized, are not explicitly modeled, and some states are dead code (`PAYMENT_SUCCESS_PENDING`, `PAYMENT_FAILED_PENDING`) because nothing in the code sets them.

## 10. Additional bugs, races, and code smells beyond requirement.md

1. Duplicate inventory success event emission
   - In `InventoryServiceImpl.processReserve(...)`, `producer.sendInventoryReserved(successEvent)` is called twice. See [InventoryServiceImpl.java](../inventory-service/src/main/java/com/deepana/inventoryservice/service/InventoryServiceImpl.java).

2. ProcessedInventoryEvent is not actually a JPA entity
   - The class lacks `@Entity` and `@Table`, even though it is used as a repository-backed `JpaRepository` entity. See [ProcessedInventoryEvent.java](../inventory-service/src/main/java/com/deepana/inventoryservice/entity/ProcessedInventoryEvent.java) and [ProcessedInventoryEventRepository.java](../inventory-service/src/main/java/com/deepana/inventoryservice/repository/ProcessedInventoryEventRepository.java).

3. Disconnected outbox scaffold
   - There is an `OutboxEvent` table and repository, but no active publisher. The direct Kafka send happens instead. See [OrderServiceImpl.java](../order-service/src/main/java/com/deepana/orderservice/service/OrderServiceImpl.java), [OutboxEvent.java](../order-service/src/main/java/com/deepana/orderservice/outbox/OutboxEvent.java), [OutboxPublisher.java](../order-service/src/main/java/com/deepana/orderservice/outbox/OutboxPublisher.java).

4. Orchestrator is effectively stateless
   - There is no persisted saga state, no recovery/resume, and no check on invalid or late events. See [SagaServiceImpl.java](../saga-orchestrator/src/main/java/com/deepana/sagaorchestrator/service/SagaServiceImpl.java), [SagaEventConsumer.java](../saga-orchestrator/src/main/java/com/deepana/sagaorchestrator/kafka/SagaEventConsumer.java).

5. Payment path is nondeterministic and not idempotent
   - `PaymentServiceImpl.processPayment(...)` uses `Random` and a fixed amount check to force failure. There is no dedupe key. See [PaymentServiceImpl.java](../payment-service/src/main/java/com/deepana/paymentservice/service/PaymentServiceImpl.java).

6. Missing key on payment success/failure messages
   - Payment producer sends to a topic without a key, which undermines ordering guarantees for a per-order workflow. See [PaymentEventProducer.java](../payment-service/src/main/java/com/deepana/paymentservice/kafka/PaymentEventProducer.java).

   - The route configuration is present, but no controller classes were found in the payment or inventory services that expose corresponding business endpoints. This means the gateway routing may work but not necessarily deliver a working public API. Evidence: [gateway-service/src/main/resources/application.yaml](../gateway-service/src/main/resources/application.yaml) and the service controller directories.

   - [Readme.md](../Readme.md) explicitly describes “Distributed Tracing”, “Fault Tolerance”, “Idempotent Consumers”, and “Optimistic Locking” but the actual code does not implement those requirements deeply or test them. This is a documentation correctness problem.

## 12. Bottom line

The code is a promising learning-project implementation, but it is not yet a correct, fully-failure-safe distributed saga system. The most important gaps are: (1) no real outbox or crash-safe event publication, (2) no persistent saga state or resume logic in the orchestrator, and (3) no consistent idempotency and ordering guarantees across all services.
